# 其余流程约束方案必要性复评（2026-10-22）

结论：继续做原建议 1 的短清单和建议 3 的最新规则返回，合成一个最小改动；先校准建议 5 的统计口径。暂缓建议 4 的 Claude hooks。ACP 需要单独验证指令送达，不能把 MCP `instructions` 当作已经证明的通用补丁。本轮只评估，没有实现额外约束。

## 证据与边界

- 原调查：[流程约束失效调查](../flow-constraints-audit-2026-10-22.md)。历史样本里，Sonnet 后续回合零 Flowly 调用 37/48；原调查指出大部分漏登记来自交付后的短回合。数字是原调查的历史结果，本轮没有重跑为新遵守率。
- 本次建议 2 的实测：[results.json](results.json)、[实现与验证报告](../delivery-constraints-2026-10-22.md)。修复后新建的 Sonnet / Codex 会话都完成了“交付 → 创建 PR 并合入”，PR #3/#4 已合入，输出回执登记成功。这证明两个指定场景通过，不证明旧会话、所有模型或普通使用中的零工具回合已经解决。
- 当前 `skills/flowly/SKILL.md` 为 19,657 bytes；建议 2 已补充回合开头的 outputs 要求，因此建议 1 是精简、消歧和突出动作触发，不需要再堆一套长规则。
- 当前 `server/tool-server.ts` 创建 MCP server 时没有 server 级 `instructions`；`shared/tools.ts` 的 `toolContextSchema` 尚无最新核心规则清单。

## 逐项判断

| 原方案 | 必要性 | 推荐范围与局限 |
|---|---|---|
| 1. 重写 skill 核心 | 值得做，低成本 | 把“改代码、跑检查、开 PR/MR、提交/合入等短回合”对应动作放在开头，删掉容易被当作例外的措辞。保留细节，不增加强制阶段流水线。降低遗忘概率，不能保证模型一定遵守。 |
| 3. get_task 返回最新清单 | 值得与 1 一起做，低成本 | 使用同一个简短规则来源，供 skill 和 get_task 使用；旧会话读卡后即可看到新要求。不要加历史推断、规则版本平台或额外消息。整轮不调用 Flowly 时仍然无效。 |
| 5. 统计前后效果 | 有必要，先校准脚本 | 这是判断后续投入的依据，不是增加产品约束。先修统计口径，再观察普通真实回合；不把两条受控复现当整体遵守率。 |
| 1 的扩展：MCP instructions / ACP 送达 | 送达验证有必要；具体实现尚未证明 | 若要宣称覆盖全部 provider，必须验证。原 ACP 缺口来自先前代码调查，本轮没有运行 ACP。先用隔离会话确认规则实际进入模型上下文，再决定改插件还是需要宿主支持。 |
| 4. Claude hooks | 暂缓 | 原建议本就以 1–3 后 Sonnet 仍明显漏报为条件。它只覆盖 Claude，还增加宿主参数传递、SDK 模式读取 settings、生命周期和命令匹配的维护成本；本轮没有证明这些路径可用。不能作为所有 provider 的核心方案。 |

### 为什么先校准统计

本轮只读核对发现，直接用原脚本做上线前后比较会产生误判：

1. `audit.mjs` 的 `registered` 仅匹配 `add_artifact:pr|cli:artifact`；`audit-codex.mjs` 仅检查 `add_artifact:pr`。它们不识别新的 `outputs` 交付路径，也不能据此判断登记是否成功。应结合成功回执、artifact IDs 和实际产物核对，不能只数尝试调用。
2. `audit.mjs` 把所有带 `acknowledgeOpen` 的交付调用计为 “up front”。现在应区分首次尝试、收到 `WORKPAD_OPEN` 后确认，以及修复检查后交付，避免把正常确认重试当成绕过。
3. 两份脚本都按 `session.createdAt >= since` 筛选。单纯传上线时间会漏掉上线前创建、上线后继续工作的旧会话；应按回合时间分段，并分别标识旧/新会话和真实/测试样本。

不需要为此建统计平台；修已有脚本，保留原始分母与失败样本即可。

### MCP instructions 的边界

[MCP InitializeResult 的协议定义](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2025-11-25/schema.ts)把 `instructions` 定义为可选字段，并说明客户端可以将它加入 system prompt；协议没有保证每个客户端都会展示给模型。因此，“ACP 连了 MCP”不能推出“ACP 模型收到了这张清单”。不能只验证 initialize 响应含字段就记为送达 PASS。

## 不建议增加的约束

- 不恢复已撤回的服务端代登记 PR、回合后自动发补登消息、要求用户改 AGENTS.md；它们违背用户已确认的插件内、当回合完成的边界。
- 不强制每回合经过所有阶段，不强制产生 idea，不新增提交/合入审批。现有 setup、workpad、nextMoves 和 outputs 的组合先用起来。
- 不把 A1r 的状态恢复当作“没有实际工作”的证据，也不靠自动提醒修补该判断。保留原始回合证据来观察即可。

推荐顺序：**校准统计口径 → 合并实施最小版 1+3 → 观察真实使用**；ACP 送达作为覆盖面验证单独做。只有真实回合仍反复出现零工具漏报时，再评估 provider 级回合开始提示。若要求每个回合都绝对遵守，就需要宿主/provider 的送达或执行控制能力；单靠工具服务无法拦住完全不调用它的回合。

本轮只做文档和源码核对，未运行新的模型测试或构建；没有用户可见产品行为变化，不涉及 onboarding 更新。前轮遗留的四个本地 Tinylink 测试 refs 仍保持原状，本轮没有重试受限清理。
