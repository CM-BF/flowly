## Fable 的核心想法

用户每次退卡时说的话，Flowly 记下来；之后每张卡交付时先照这些话查一遍，查过了才把卡交到用户手上。用户只看到三样：卡面 “已检查 ✓ / 已退回 ↩”、一份用自己原话写成并带“抓到几次 · 误判几次”的检查清单、Done 仍由人决定。Fable 认为 P1–P3 的服务端骨架是对的，问题在采用路径：默认关、第一次体会到价值要几周、学习靠批处理、操作都在设置页里。

## 建议采纳

### 第一批（改动小、价值大）

1. **退卡当下学**：
   - 不单独起模型调用，搭卡片总结的便车。卡片总结默认开启，每轮结束都会跑，输入里本来就有用户这一轮说的话（TASK-SUMMARY-SPEC §2）。
   - daemon 在回合结束时就能确定这一轮是不是交付后返工：开始时 A1 把卡从 In review 拉回，并且没有被 A1r 还原。
   - 只有返工的回合，才在总结提示里附上“已有检查与近期退回事项”（最多 20 行短句）。总结输出多一个可选字段：这句话是在纠正已交付的工作时，用一句短语归纳它；与列表里某条是同一件事时，原样给出那一条。
   - daemon 记录事项和计数。同一事项出现在第二张卡上时，在该卡的评审区块底部给一行：“这件事已在 2 张卡上退过，以后每张卡都查？[每张卡都查] [不用]”。
   - 关闭卡片总结的项目没有即时学习，退回到 Insights 定期运行。
2. **检查用用户原话命名并记账**：规则行显示“抓到 N 次 · 误判 M 次 · 最近 X 天前”，从 `review_finished.results` 聚合。
3. **误判的出路**：
   - 失败行加“不算问题”，只对本卡生效，并记一次误判。
   - 30 天内误判 2 次的检查自动暂停，问一次保留还是删除。
4. **成本看得见**：评审模型未设置时用摘要模型列表，不再回退到项目默认的 agent 模型。每次评审在卡上标模型和 token。
5. **交付前就知道要查什么**：生效的检查写进 session 的第一条指令。
6. **去掉 `guidance`**。
7. **同一提交 + 同一 workpad 版本的重复交付复用上次结果**。

### 第二批（中等工作量）

- **共享目录**：只按本卡 session 改过的文件判断；命令失败只展示，不退卡。
- **证据核对**：读 timeline，核实 workpad 里标 pass 的命令是在最后一次改文件之后跑的。Claude 的 shell 条目没有退出码，只能可靠判断先后顺序；拿不准时判“不适用”。
- **agent 申诉**：交付时带 `disputes`，由用户裁决。
