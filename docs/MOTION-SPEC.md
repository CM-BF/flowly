# Board feedback and navigation motion

Status: authorized by the user's 2026-10-14 request. This amends UI-UX, session UX and session-chip presentation; single-root and Phase 2 business contracts remain current.

## Observable behavior

- A successful status move shows Paseo's native success toast (`Moved to In progress`, etc.), for the host default 2,200 ms. It adds no board row or layout height. Mouse drop and action/status controls use this feedback. A rejected mutation retains its actionable error and never shows success. Another success replaces the previous toast through the host API.
- Board lane labels, counts, empty/drop hints and card text disallow selection through React Native Text, including while a mouse drag crosses lanes. Task details, conversation output and editable inputs keep their existing selection behavior. No DOM selection APIs or global event handlers.
- Opening a task sidebar slides/fades it in from the right; closing slides/fades it out faster. Compact detail uses the same bounded transition. Closing immediately disables interaction, conversation subscriptions and deferred native navigation, even while its visual shell exits. Rapid reopen reverses the exit; stale animation completions cannot close a new target.
- Opening a session preview slides/fades new content forward. Back reveals task detail in the reverse direction. Different card/session and native Task chip requests use the same transition. Selection, drafts, pending operation locks and one-time chip consumption retain existing semantics; animation does not delay selection or a write.
- Project/status changes have a short content transition. Host Modal/sheet, native screen/workspace/session navigation and toast retain Paseo's own transitions; do not layer a second animation over host-owned UI. Plugin-owned tool disclosure gets a bounded reveal.
- Drag feedback lifts/fades the ghost and subdues the source card. Pointer tracking is immediate, without easing or timers on coordinates. Eligible lane emphasis transitions quickly. Release/cancel fades the non-interactive ghost; committed card arrival transitions in its destination. Captured-revision single-write rules remain unchanged. Another drag supersedes an exiting ghost.

## Motion language and constraints

Operate surface: motion explains spatial relationships and confirms actions. Share a React Native Animated implementation and durations: feedback 120 ms, forward navigation 220 ms, reverse/exit 160 ms. Decelerating easing, no bounce, loops or list choreography. Animate opacity/transforms only; resizing and drag coordinates remain direct. Use native driver on native platforms and supported JS driver on web. No runtime dependency or private host import.

Read `AccessibilityInfo.isReduceMotionEnabled()` and observe `reduceMotionChanged`. Default to reduced motion until the asynchronous preference is known; keep that safe default on failure. Reduced motion applies final states immediately, while toast/error/state feedback remains visible. Stop animations/listeners and guard completion on interruption, replacement, StrictMode replay and unmount. Polling/streaming text must not replay navigation animation.

An exiting sidebar retains its presentation until exit finishes. Preview receives an explicit inactive flag: no subscription, polling, send/read/tool action or delayed native navigation. Pending operations already sent are not cancelled or duplicated. Back unmounts its old preview immediately so late membership checks cannot navigate. Animation completion never changes server state or acknowledges attention.

## Architecture

No schema/RPC/storage migration or resource provisioning. `client/motion.tsx` owns preference, interruption-safe presence and shared reveal/progress primitives. Board owns drawer presence, host toast and content transition; drawer owns session transition; columns/cards own drag feedback. Client remains React Native only. AGENTS.md requires motion for future plugin-owned opens/closes/navigation/drag feedback, reduced-motion support and cleanup coverage.

## Rest state carries no animated props (2026-10-20)

User report: going Back from a session sometimes left the card details shifted about 18 pt (Android phone). Cause: with the native driver on Android's new architecture, the animation writes `opacity`/`transform` straight to the native view, behind React. When that native write outlives the animation (interrupted, dropped, or overwritten by a commit made mid-transition), setting the value back to its rest value is not a prop change React can see, so nothing corrects the view. The earlier fixes (stable interpolation nodes, a final-value sync, one signed offset) narrowed this but could not close it.

Rule: a long-lived view attaches its animated `opacity`/`transform` only while it is moving, and renders without them at rest. Removing them is a real prop change, so the commit always resets the view to identity. Applied to `MotionReveal` (moving between a key change and the newest animation's end, finished or stopped), `Enter` (until its entrance ends) and the board's drawer container (`useMotionPresence().settled`: shown and done entering). Short-lived surfaces that unmount after closing (menus, popovers, sheets) keep their props. Test: `docs/verification/fixtures/motion/motion-primitives.test.tsx` (props attached while moving, dropped at rest, an older reveal's late end never resets a newer one).

## Running state: dot-matrix sweep (2026-10-24, user request)

The rule above ("no loops") predates this; the user asked for the working state to be visible in motion, so it is the one standing exception beside the breathing `PulseDot`. History, so the same ideas are not tried again: a rotating beam with an accent-tinted ring (rejected: selected cards could not be told apart; uneven speed, visible steps), a comet travelling round the border ("ordinary"), and a gradient sheen on cards plus a gradient shimmer on session rows (the row shimmer was liked as restrained and elegant). The user then asked for dot-matrix motion and, from three prototypes (full-card dot sweep, LED strip along the bottom, 3×3 dot spinner), chose the **dot sweep for both board cards and session rows**.

- **What it looks like** (`RunningDots`, `client/running-motion.tsx`): a grid of 2 px dots, 8 px apart, lies hidden under the content. A wave leaning right towards the top lights it from left to right in about 1.4 s; each dot rises quickly to 85 % accent and fades with a soft afterglow about eight slanted lines long; then the dots rest dark for about 1 s of the 2.4 s loop (user tuning 2026-10-24: faster, wider, brighter, shorter pause than the first 1.8 s sweep / 60 % / 1.8 s rest). Each card or session sweeps at its own point of the loop (hash of its id), so a board of running cards does not light up in unison.
- **Where**: board cards while any of their sessions is running or starting (clipped to the card's rounded inside, under the content; the card's own border is untouched, so a selected card keeps its solid accent); session rows in the card detail (including subagent rows) while that session is running, replacing the earlier gradient shimmer; the row's breathing dot stays. The session view's header (title and state above the transcript) carries the same sweep while that session is running (user request 2026-10-24), same seed as its row.
- **Drawing**: plain views only (no gradients, no background-image styles): the dots are laid out once per size and grouped into the slanted lines the wave lights together; each line is one layer whose opacity follows the wave.
- **Cost**: all sweeps share one 0 → 1 timing loop (`useMarquee`, `client/motion.tsx`) on the native driver, started by the first mounted one and stopped and reset by the last; nothing runs while no card, row or session header is running. The loop restarts itself when it ends on its own and when the app returns to the foreground (`AppState` active), so a sweep never stays dark until a reload. Only opacity animates, one animated layer per slanted line (about 40 per card, 50 per row); a 280 × 130 card holds about 500 static dots, re-laid out only when its size changes, and the component is memoised so board updates do not re-render it.
- **Reduce Motion**: nothing is drawn; the static "N running" signal and the dot remain.
- **Geometry priority**: only compact host windows (<760 logical width, using the existing breakpoint) pause decorative clocks while a height lease is active. Wide windows keep the same running loop/phase through card navigation and height changes; redundant lease/resize notifications do not restart it. Compact resumption still begins a fresh lap at phase 0 after the microtask guard. One shared window-size listener exists only while height-state consumers are subscribed and is cleaned up with the last; Reduce Motion and last-user cleanup remain. See [current continuity policy](MOBILE-SMOOTHNESS-SPEC.md#7-用户反馈修正宽屏保留共享动画连续性) and [bounded Samsung evidence](MOBILE-SMOOTHNESS-SPEC.md#6-执行结果与边界).
- **Evidence**: `client/running-geometry.test.ts` (seamless loop keys, afterglow shape and wrap, grid placement and slant, per-id offsets). Web rendering checked in a standalone react-native-web 0.21 page (Chromium via `docs/promo/shot-lib.mjs` `launch`), dark and light, selected and not, 60 fps steady (rAF p95 16.7 ms); frames and the three prototypes in `docs/verification/running-motion/`. Not yet seen in the Paseo app or on a phone.
