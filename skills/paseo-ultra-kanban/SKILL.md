# Paseo Flowly

Use this skill when working in the workspace of an attached Flowly card.

- Read kanban_get_task before starting a work phase and before reporting after long work. The connection identifies your card/session. Do not choose another card or infer the task from cwd, title, or labels.
- Follow scope.repoPaths and scope.directories. New cards work at the native Paseo project root, which may contain child repositories managed by the user. Older cards can retain a read-only legacy scope; follow the listed directories. A worktree isolates the Git project root only. Provider permissions still apply. Report denied access.
- When work actually starts, set the work stage that matches it: design (plans, specs, research), development (implementation) or test (verification). You decide from the instructions whether to start with design or go straight to development. Keep the stage current as the work changes: switch to development as soon as you start changing code, to test when you verify, and back when needed; never deliver implementation work from design. Report checkpoints and individual contributions with kanban_report_progress. A single session finishing its part does not prove the whole card is finished.
- When you need the user to decide or answer something, report kind=question with one clear question (offer options when you can), then end your turn. The card shows "Needs you"; the user's reply starts your next turn. Starting a turn after a user message also moves the card automatically: from in_review to development (review feedback is usually rework), from blocked back to its previous work stage. That stage is only a guess: at the start of every turn, compare it with the work you are about to do (for example, rework of the implementation is development) and set the right stage first if it differs.
- When your work reveals worthwhile next steps the user did not ask for, propose them with kanban_propose_idea, usually when you deliver. Set scope=here for an extension of this card's goal that this card's session can continue with its current context (the user may send it back to this session as an instruction), and scope=new for divergent work that deserves its own card (a bug found on the way, a refactor, a separate feature). Work this card already requires is not an idea; do it. Propose at most 3 per delivery and check ideas in get_task first. Put the files, branches and findings a new card would need in context: its agent cannot see this conversation. Ideas are suggestions only; never start one or create cards yourself. If it returns IDEAS_DISABLED, the user turned Ideas off: mention those next steps in your reply instead and do not retry.
- When you end a turn and there are clear next steps for this session (verify the change, commit and push, continue with the next stage, fix what you just found), call kanban_suggest_next_moves once with the 1-3 messages the user is most likely to send you next, recommended first: a short label in the user's language and the full prompt written as the user's instruction to you. Flowly shows them above the message box; picking one only fills it in and the user sends it. They expire when the user's next message starts a turn; a later call in the same turn replaces them. Still mention the options in your reply. Skip it when nothing needs the user. Questions go through kind=question, and divergent work through kanban_propose_idea, not next moves.
- links in kanban_get_task lists cards linked to yours (follow_up_of, follow_up, blocks, blocked_by, related) with their lane; you only see their title and status. If a blocked_by card is not resolved, say so before starting and follow the user's direction; it is a hint, not a reason to set blocked by itself. You cannot create or remove links.
- artifacts in kanban_get_task lists the card's inputs (material it works from) and outputs (deliverables so far), each marked createdBy user or agent. Inputs the user added are part of the task: read every one before you start (files through absolutePath, links with your web tool when you have one), and treat its note as an instruction about how to use it. unread=true marks artifacts added or edited since this session last read the card; at the start of every turn read kanban_get_task and handle unread inputs first. If an input cannot be read (missing, link unreachable or behind a login, no web access), say so in your reply instead of guessing its content. When you deliver, name the inputs you used. When you produce a deliverable (a spec, report, exported file, PR link, verification evidence), register it with kanban_add_artifact role=output; register an outside document or link you relied on as role=input. Do not register every source file you changed; the workspace diff shows them. You may remove only artifacts an agent added (kanban_remove_artifact). If it returns ARTIFACTS_DISABLED, list the deliverables in your reply instead and do not retry.
- Once you understand the scope, tag the card with kanban_set_tags: 1-4 short lowercase tags for the functional areas it touches (a module such as "drawer" or "session-composer") and the directions it serves ("performance", "a11y", "mobile"). Not the task type, status or priority. Reuse a tag from projectTags in kanban_get_task when one fits instead of inventing a synonym, and adjust the tags if the scope changes. You may remove only tags an agent added. When proposing an idea you may suggest tags for it.
- If task.type is missing in kanban_get_task, set it with kanban_set_type once you understand the work: feature (new behavior), bugfix (wrong behavior fixed), research (investigation without a shipped change), refactor (restructuring without behavior change), docs (documentation only) or chore (build, tooling, dependencies, maintenance). Never change a type that is already set; TYPE_ALREADY_SET means the user or an agent chose it, so keep it and do not retry.
- Use blocked only when the overall task cannot proceed; otherwise report kind=blocker with its impact and the required input. Resume with the work stage you continue in. Deliver the overall result to in_review, explaining changes, verification, unrun checks and remaining issues. Done/Cancelled/Backlog/Todo are human decisions. The project's lanes define its workflow: only use statuses listed in allowedStatuses, and refer to lanes by their names in lanes.
- Copy revision.task/project and the complete request object into each write. Do not edit signed fields. A progress note does not change task revision; status changes and human edits do. Project edits also invalidate an old context.
- For REVISION_CONFLICT or REQUEST_EXPIRED, re-read and decide whether the intended action is still valid. Never just replace revisions and overwrite the human's work.
- For uncertain timeout/disconnection, repeat the same request and parameters to obtain its receipt. A replay acknowledges the original commit, not that its old status is still current. Never blindly generate a new request to repeat an uncertain write.
- Prefer the MCP tools when present. Otherwise use the supplied absolute CLI/context-file command. Run current --save-request <your-private-snapshot-file>, then status <state> or note with --request-file pointing to that snapshot and a nonempty --note, or idea with --request-file, --title, --detail, --rationale and optional --context/--type/--priority/--scope, or artifact with --request-file, --role input|output, --target and optional --title/--note, or artifact-remove with --request-file and --id, or tags with --request-file and --add/--remove (comma-separated), or set-type <type> with --request-file, or next-moves with --request-file and --moves '<JSON array of {label, prompt}>'. After success save a fresh current snapshot before the next write. Do not reuse a snapshot for a different action after it committed.
- If tools are unavailable, explain the limitation in your reply; do not assert that a card transition succeeded. Never edit board.json, tool credentials, global MCP configuration or another session's context file to work around an error.
- Session running/idle/turn completion is independent of card business status. Do not automatically hand off, assign another agent, or complete the project.
